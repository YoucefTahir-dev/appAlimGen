# CY-09 et lot D — contrôle des prix et chaîne de livraison

Date de qualification locale : 22 novembre 2026.

## CY-09 — politique appliquée

- Le tarif de référence reste calculé par le serveur selon le type de client
  et le conditionnement carton/pièce.
- Toute hausse ou baisse par rapport à ce tarif exige la nouvelle permission
  explicite `commerce.override_sale_price`.
- Cette permission est opt-in : elle n'est ajoutée automatiquement à aucun
  ancien rôle administrateur, gestionnaire ou vendeur. Un superutilisateur la
  possède selon le comportement Django habituel.
- Le prix d'achat reste un plancher absolu, y compris pour un utilisateur qui
  possède la permission de dérogation.
- Une ancienne ligne négociée peut être sauvegardée sans nouveau droit si le
  produit, le conditionnement, la quantité et le prix restent tous identiques.
  Toute modification de cette ligne réactive le contrôle.
- Chaque nouvelle dérogation autorisée crée un `AuditLog` avec auteur, date,
  facture, produit, tarif attendu et prix appliqué.
- Web, API et Android appliquent la même règle. Android rend le champ prix en
  lecture seule sans la permission ; le serveur reste l'autorité finale pour
  les clients anciens, modifiés ou concurrents.

La migration `commerce.0019_alter_sale_options` ne modifie aucune donnée
métier et ne contient qu'un `AlterModelOptions`. Elle est approuvée par
empreinte dans le garde-fou de pré-déploiement ; `post_migrate` crée la
permission Django sans l'accorder à un compte ou un rôle.

## Lot D — chaîne de livraison

Le workflow Django fixe également PostgreSQL 16 sur le digest OCI
`sha256:3950ad7c3148ca2175ef1b6c36c9efbf78957ae8fbe8b3a5d7c35af50500382f`
(image officielle 16.16 observée le 22 novembre 2026), avec concurrence et
délai maximal explicites. Un test empêche le retour à un tag de service mutable.

- Les actions externes backend sont verrouillées sur des SHA Git immuables et
  chaque workflow déclare `contents: read` par défaut.
- Un test empêche le retour d'un tag flottant (`@v4`, `@main`, etc.) ou
  l'absence de permissions explicites.
- Le client Windows est compilé et testé depuis son `Cargo.lock` sur la cible
  Windows. La CI refuse la réapparition de `glib` ou `proc-macro-error`, absents
  du graphe qualifié pour `x86_64-pc-windows-msvc`.
- Aucun installateur Windows non signé n'est publié. Une diffusion Windows
  officielle reste conditionnée à un certificat Authenticode OV/EV détenu par
  l'entreprise ; aucun faux certificat ni secret n'est créé par le dépôt.
- Le dépôt Android possède des workflows distincts de CI et de publication.
  Flutter 3.44.4 et toutes les actions sont verrouillés. La publication exige
  les quatre secrets de signature, vérifie l'APK avec `apksigner`, génère un
  SHA-256 et un manifeste de provenance lié au commit, puis retire le keystore.
  Sans secrets, le job et Gradle échouent fermement ; aucune clé debug n'est
  acceptée pour une release.
